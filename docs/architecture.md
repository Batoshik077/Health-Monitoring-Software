# Архитектура AstroHealth

Главный принцип: **борт решает сам**. Тревога и протокол действий появляются у астронавта за секунды; Земля получает данные с задержкой и нужна для консультаций, а не для решений.

## 1. Общая схема

```
┌──────────────────────── backend (FastAPI, один процесс) ────────────────────────┐
│   SimClock — часы миссии: все модули живут по ним, ускорение ×1…×600            │
│                                                                                 │
│   Simulator ──▶ Analytics ──▶ Alerts ──▶ Guidance ──▶ Onboard State ──WS──▶ /me, /alerts, /crew
│                                                          │ outbox              │
│                                                          ▼                     │
│                                    Outbox + Link Simulator                     │
│                                    задержка, обрыв, приоритеты P0/P1/P2        │
│                                                          ▼                     │
│                                    Ground State (только «долетевшее») ──WS──▶ /ground
│                                                                                 │
│   Director API ◀── /director (пульт сценариев)         SQLite: тревоги, журнал │
└─────────────────────────────────────────────────────────────────────────────────┘
```

Две ключевые идеи:

- **SimClock.** Все модули берут время из общих часов миссии. Ускорение ×60 превращает 12 минут задержки связи в 12 секунд, а несколько ночей сна — в минуту демо.
- **Отдельный Ground State.** Земля видит только то, что прошло через симулятор канала. Задержка на демо настоящая, а не нарисованная.

## 2. Модули бэкенда

| Модуль | Что делает |
|---|---|
| **SimClock** | Часы миссии, скорость меняется на лету. Тик = 1 секунда времени миссии. |
| **Simulator** | Мок-данные: виртуальные датчики 4 астронавтов и модулей корабля. Сигнал = личная норма + суточный ритм + шум + активность. Сценарии ЧП из `config/scenarios/` накладываются поверх. |
| **Analytics** | На каждый тик: качество сигнала, баллы NEWS2, отклонение от личной нормы (z-score), индекс готовности 0–100, накопленная доза радиации, статус по системам организма. Пороги — из `config/thresholds.yaml`. |
| **Alerts** | Тревога, если условие держится N секунд. Дедупликация, гистерезис, цикл `active → acknowledged → resolved`, эскалация CRITICAL командиру через 30 с. Объяснение причины в каждой тревоге. |
| **Guidance** | Связывает правило тревоги с протоколом из `config/protocols/`: шаги, кого позвать, когда перепроверить. Ежедневные советы (сон, тренировки, отдых). Проверяет, стало ли лучше после действия. |
| **Outbox + Link Simulator** | Очередь на Землю: P0 тревоги, P1 поминутные сводки, P2 подробные данные. Задержка по профилю (МКС 0 с, Луна 1.3 с, Марс 3–22 мин), обрыв, ограниченная пропускная способность, повторная отправка. Сообщения врача идут обратно с той же задержкой. |
| **Хранение** | Живые показатели — в памяти (кольцевой буфер ~24 ч на астронавта). SQLite — тревоги, протоколы, опросники, симптомы, тренировки, журнал, сообщения. |

## 3. Системы организма и угрозы из задачи

| Из задачи | Как отслеживаем | Как действует астронавт |
|---|---|---|
| Радиация | Суточная и накопленная доза, % от лимита 600 мЗв, всплески | При солнечной вспышке — в защищённый модуль, сократить выходы |
| Изоляция и замкнутость → психика | Ежедневный опросник (настроение, стресс, усталость), сон, тренды | Советы по отдыху и сну, связь с близкими и психологом, сигнал медику |
| Изменённая гравитация → кости и мышцы | Журнал тренировок против плана, оценка потери костной массы по дням полёта | Напоминания и план тренировок, предупреждение при недоборе |
| Сердечно-сосудистые события | Пульс, давление, SpO₂, дыхание, NEWS2, личная норма | Протокол по тревоге: что проверить, кого позвать, когда перемерить |
| Иммунные изменения | Тренд температуры, дневник симптомов | Наблюдение, изоляция от экипажа при инфекции, сигнал медику |
| Замкнутая среда | CO₂, O₂, давление по модулям | Сменить модуль, проверить вентиляцию, сообщить командиру |

## 4. Данные

Все данные в прототипе — **мок-данные** от симулятора. Реальных датчиков нет; генератор делает сигналы правдоподобными, а сценарии воспроизводят ЧП одинаково на каждом прогоне.

| Источник | Показатели | Частота |
|---|---|---|
| Носимый датчик (симуляция) | Пульс, SpO₂, частота дыхания, систолическое давление, температура, активность | 1 раз в секунду |
| Сон | Длительность | 1 раз в сутки |
| Датчики среды по модулям | CO₂, O₂, давление, температура, мощность дозы радиации | 1 раз в секунду |
| Опросник | Настроение, стресс, усталость, качество сна (0–10) | 1 раз в сутки |
| Дневник симптомов | Вид, тяжесть, заметка | по событию |
| Журнал тренировок | Минуты, тип, нагрузка | по событию |
| Расчётные | NEWS2, z-score, готовность, накопленная доза | каждый тик |

Пороги и факты с источниками — в [`thresholds-and-facts.md`](thresholds-and-facts.md), конфиг — в [`../config/thresholds.yaml`](../config/thresholds.yaml).

### Формат WebSocket

Бэкенд 4 раза в секунду (реального времени) рассылает **снимок состояния** целиком — фронтенду не нужно склеивать события.
`/ws/onboard` отдаёт снимок борта, `/ws/ground` — снимок Земли (только «долетевшее»).

```json
{ "type": "snapshot", "side": "onboard", "t": 3605.0, "time": "2031-03-04T09:00:05Z", "speed": 60,
  "crew": [{ "id": "a3", "name": "Инженер", "vitals": { "hr": 87, "spo2": 86, "rr": 21, "sbp": 112, "temp": 36.4 },
             "news2": { "total": 5, "parts": { "spo2": 3, "rr": 2 }, "level": "warning" },
             "z": { "hr": 8.1 }, "readiness": 54, "status": "red",
             "systems": { "cardio": { "status": "yellow", "detail": "пульс 87, давление 112" } },
             "todo": [{ "kind": "protocol", "text": "Пройти протокол: Низкий кислород в крови" }] }],
  "modules": [{ "id": "lab", "co2_mmhg": 2.2, "co2_avg_1h": 2.1, "o2_pct": 21.0, "pressure_kpa": 101.3 }],
  "alerts": [{ "id": "al_1", "rule": "spo2_critical", "severity": "critical", "subject_name": "Инженер",
               "message": "SpO₂ 86 % — ниже 88 % дольше 30 с", "status": "active", "protocol_run_id": "pr_1" }],
  "protocol_runs": [{ "id": "pr_1", "title": "Низкий кислород в крови", "steps": ["…"], "steps_done": [true, false] }],
  "link": { "up": true, "delay_s": 720, "queue": { "p0": 0, "p1": 34, "p2": 210 }, "in_flight": 280 },
  "scenarios": [{ "id": "hypoxia", "target": "a3", "elapsed_s": 95 }] }
```

Внутри канала связи на Землю идут пакеты `alert`, `protocol_run` (P0), `summary` и `env` (P1, раз в минуту) и `raw` (P2, раз в 10 с).

### Таблицы SQLite

```sql
astronauts     (id, name, role, baseline_json)
alerts         (id, astronaut_id, time, severity, rule, message, status,
                acknowledged_by, resolved_at)
protocol_runs  (id, alert_id, protocol_id, steps_done_json, started_at,
                recheck_at, outcome)
surveys        (id, astronaut_id, time, mood, stress, fatigue, sleep_quality)
symptoms       (id, astronaut_id, time, kind, severity, note)
exercise_log   (id, astronaut_id, date, minutes, type, load)
medical_log    (id, astronaut_id, author, time, text)
messages       (id, direction, sent_at, delivered_at, priority, payload)
```

## 5. API

```
REST — астронавт
GET  /api/me/{id}                      статус по системам организма, готовность, советы на сегодня
POST /api/surveys                      ежедневный опросник
POST /api/symptoms                     дневник симптомов
POST /api/exercise                     отметка тренировки
GET  /api/alerts/{id}                  тревога + протокол действий
POST /api/alerts/{id}/ack
POST /api/protocol-runs/{id}/steps/{n} шаг протокола выполнен
POST /api/alerts/{id}/resolve

REST — экипаж и корабль
GET  /api/crew                         список экипажа и текущий статус
GET  /api/crew/{id}                    карточка: показатели, NEWS2, готовность, доза
GET  /api/crew/{id}/history?metric=hr&minutes=60
GET  /api/environment                  модули корабля
GET  /api/alerts?status=active
GET  /api/link                         статус связи, задержка, размер очереди

REST — Земля
GET  /api/ground/...                   то же из Ground State (с задержкой)
POST /api/ground/messages              сообщение врача на борт

Director (пульт)
POST /api/director/scenario/{name}     {astronaut_id, intensity}
POST /api/director/clock               {speed: 60}
POST /api/director/link                {up: false} или {profile: "mars", delay_s: 720}
POST /api/director/reset
POST /api/director/scenarios/stop      остановить все сценарии
GET  /api/director/scenarios           список сценариев

WebSocket
/ws/onboard                            поток для экранов борта
/ws/ground                             поток для Земли: только «долетевшие» данные
```

## 6. Экраны

| Путь | Экран | Что на нём |
|---|---|---|
| `/me` | **Моё здоровье** (главный экран астронавта) | Статус по системам организма светофором, индекс готовности, «что сделать сегодня» |
| `/me/checkin` | Ежедневная самопроверка | Опросник 30 секунд, симптомы, отметка тренировки |
| `/alerts/:id` | **Тревога и протокол** | Что случилось простыми словами, чек-лист, «Сделано», перепроверка через N минут |
| `/crew` | Обзор экипажа (медик, командир) | 4 карточки: статус, пульс, SpO₂, NEWS2, готовность |
| `/crew/:id` | Карточка астронавта | Живые графики, личная норма, история тревог, доза, сон, тренировки |
| `/environment` | Корабль | CO₂, O₂, давление, радиация по модулям |
| `/ground` | Mission Control (Земля) | Те же данные с плашкой «N мин назад», статус канала, рекомендации |
| `/director` | Пульт сценариев | Сценарии, скорость времени, обрыв связи, сброс |

## 7. Пример: гипоксия от кнопки до Земли

1. На `/director` нажимаем «Гипоксия → Инженер».
2. Simulator плавно снижает SpO₂.
3. Analytics: SpO₂ ≤ 91 % даёт 3 балла NEWS2, растут пульс и дыхание, сумма доходит до 7.
4. Alerts: через 30 с — CRITICAL со звуком на экране инженера.
5. Guidance: открывается протокол `hypoxia`, астронавт отмечает шаги; через 2 минуты система перепроверяет SpO₂.
6. Тревога уходит в очередь P0; Link Simulator держит её 12 минут времени миссии.
7. На `/ground` тревога появляется, когда астронавт уже справился. Это и есть смысл задачи.

## 8. Как будет в продакшене (слайд для питча)

- Реальные носимые устройства (например, умная футболка вроде Astroskin) по BLE → MQTT.
- Временные ряды в TimescaleDB, модели аномалий на борту (ONNX).
- Связь через DTN (Delay/Disruption Tolerant Networking).
- Шифрование, разграничение доступа, журнал аудита медицинских данных.
- Протоколы пишут и утверждают врачи полётной медицины.
